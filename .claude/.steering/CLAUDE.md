# steering design.md 構成ルール

design.md 肥大化・見通し悪化防止。
issue-137 design.md（決定事項ログ 150行超）を教訓に新設。

## 必須セクション・順序（design.md）

1. 目的
2. 背景・制約
3. （プロジェクト固有セクション。ゲーム内容・基本構成案 等）
4. 懸念・リスク

実装計画は `backlog.md`、決定事項は `decision-records.md` へ常に分離。
design.md 側にはセクション自体設けない（下記、いずれも同ディレクトリ常設）。

## backlog.md（実装計画）

未完了（`- [ ]`）項目のみのフラットなリスト。完了したら削除する（`_closed` 運用と同じ思想、履歴は decision-records.md 側に残る）。
「毎回どこが次か探す」を無くすのが目的、完了済みとの混在は不可。

チェック項目本文 1 行相当に留める。
経緯・調査ログ・修正詳細を書かない → `decision-records.md` へ（参照記法は下記）。

項目内に要素（目的・手段・対象・条件等）が複数ある場合、1 文へ詰め込まず子箇条書きへ分解する（`~/.claude/rules/markdown.md` 構造化記述ルール準拠）。
分解はあくまで同一情報の要素整理、経緯・調査ログ等の分量増加を伴う追記は不可。

関連する decision-records.md エントリがある場合、項目の子要素（ネストした箇条書き）として `(decision-records.md 日付)` を付記する。
本文末尾への埋め込みでなく子要素にするのは、本文と参照を視覚的に分離するため。
backlog.md だけを読んでも必要な過去決定に辿り着けるようにするのが目的、decision-records.md 全体を都度参照する事態を避ける。

項目追加時、既存項目含め作業順を軽く見直す。
リストの並び = 着手順に保つ（先頭から順に着手すれば済む状態）。

- 観点: 依存関係（前提となる項目を先に）・関連項目の隣接配置
- 並替えが要らなければ末尾追加のまま可
- 並替え理由が非自明な場合のみ decision-records.md へ残す

## decision-records.md（決定事項）

1 エントリ 1〜2 行目安。
試行錯誤の逐次記録・作業ログはコミットメッセージへ譲る。
例外: 原因調査の結論・トレードオフ判断根拠 等、後日の再発防止・再検討に効くもの残してよい。

同一トピック追記連続時、新規追記でなく既存エントリ更新（上書き・統合）も可。
時系列積み上げのみに固執しない。

アーキテクチャ選択に相当する重要判断の ADR 化検討は [docs/concept/implementation/adr/README.md](../../docs/concept/implementation/adr/README.md) 参照。

## 懸念・リスク

解消済み項目、打消し線でなく削除。
経緯残したい場合は decision-records.md 側へ。
現在有効な懸念のみ残す。

## ファイル間の参照記法

「詳細は」「参照」等の枕言葉不要。
`(ファイル名 場所)` の形だけで足りる。
例: `(decision-records.md 2026-09-12)`。
もっと短くてもよい。
